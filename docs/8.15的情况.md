# 二、配置连接信息

进入左侧的“连接设置”。

这里有三个字段。

## 1. FastAPI 服务地址

开发环境推荐填写：

```text
/
```

这表示使用 Vite 的同源代理。

如果要让前端直接请求另一个后端，可以填写：

```text
http://192.168.1.10:8000
```

直接连接不同域名或端口时，后端还需要配置 CORS。当前本地开发推荐继续使用 `/`。

## 2. 操作者标识

例如：

```text
admin
```

或：

```text
skill-reviewer
```

前端会把它放入每个请求的：

```http
X-Actor: admin
```

后端中间件会把操作者写入 API 审计日志。

## 3. 管理员密钥

如果后端 `.env` 配置了：

```env
ADMIN_API_KEY=your-secret
```

这里就需要填写相同的值。前端会发送：

```http
X-Admin-Key: your-secret
```

后端对以下写操作进行保护：

- POST
- PUT
- DELETE

查询类 GET 接口不需要管理员密钥。

配置保存在浏览器 `localStorage`，不会进入后端系统快照。

# 六、连接 Agent

创建多个 Agent 后，点击“连接节点”。

选择：

- 起点 Agent
- 终点 Agent
- 或选择 `END`

例如：

```text
planner → researcher
researcher → writer
writer → reviewer
reviewer → END
```

普通连接对应：

```text
POST /api/connections
```

请求结构大致为：

```json
{
  "source_id": "planner-agent-id",
  "target_id": "researcher-agent-id",
  "conditional": false
}
```

`END` 是图执行结束哨兵。

后端会把 Agent 的定义关系转换为图执行关系：

```text
AgentSpec
    ↓
Node
    ↓
StateGraph.add_edge()
    ↓
CompiledGraph
```

当前画布根据 Agent 数量自动排列节点，适合查看和配置编排。后端本身也支持条件边，但当前前端主要提供普通执行边的创建操作。


```json
  "agent_id": "agent-id"
```

它不表示这个 Agent 自动拥有所有其他 Agent。后续执行顺序仍然由连接关系决定。

# 八、理解父子 Agent 与执行连接

后端同时存在两种关系。

## 管理关系

```text
父 Agent
└── 子 Agent
```

通过：

```text
POST /api/agents/{agent_id}/sub-agents
```

创建。

## 执行关系

```text
Agent A → Agent B
```

通过：

```text
POST /api/connections
```

创建。

二者含义不同：

- 父子关系表示组织层级。
- 执行边表示运行顺序。
- `auto_connect=true` 时，创建子 Agent 的同时会创建执行边。
- 运行中的父 Agent 不会自动创建新的 Agent。
- 当前系统仍是执行前完成编排，再运行已经编译好的图。

# 十一、发起正式运行

进入“运行中心”，点击“发起运行”。

## 1. 选择工作流

可以选择已经保存的工作流。

如果选择“当前内存编排”，后端会使用当前加载的 Orchestrator。

## 2. 填写运行输入

输入必须是 JSON。例如：

```json
{
  "input": "分析当前智能体项目的技术架构，并生成一份风险评估报告",
  "user_id": "user-001",
  "task_type": "architecture_review"
}
```

核心任务文本建议放在：

```json
{
  "input": "任务内容"
}
```

因为 `AgentRuntimeFactory` 会优先读取 `state.input`。

## 3. 设置递归上限

默认：

```text
50
```

它限制图执行的最大超步数，用来避免条件循环或错误连接造成无限执行。

## 4. 启动运行

对应：

```text
POST /api/runs
```

后端先创建 `RunRecord`：

```text
created
    ↓
queued
    ↓
running
    ↓
succeeded / failed / canceled
```

然后通过 FastAPI `BackgroundTasks` 执行图。

运行存储实现位于：

[workflows.py](/D:/PythonProject/long_task_1/long_task_1/engine/modules/workflows.py)

默认目录：

```text
long_task_1/runs/executions
```

# 十二、后端如何执行一个 Agent

后台运行开始后，后端会加载指定工作流，并调用：

[agent_runtime.py](/D:/PythonProject/long_task_1/long_task_1/engine/modules/agent_runtime.py)

每个 `AgentSpec` 会被转换成一个真实 `Node`。

运行 Prompt 大致由以下部分组成：

```text
当前 Agent
Agent 描述
任务输入
上下文账本
可复用技能
记忆上下文
```

随后构造 `ResourceRequest`，交给：

```text
AdaptiveResourceScheduler
    ↓
ExecutorRegistry
    ↓
ResilientInferenceRunner
```

资源调度可能选择：

- device：本地模型
- edge：边缘模型
- cloud：云端 OpenAI-compatible 模型

执行失败时会根据配置重试或回退。

因此运行成功后，应在输出的 `messages[].result` 中重点查看：

```json
{
  "executor": "OpenAICompatibleCloudExecutor",
  "model": "deepseek-v4-flash",
  "success": true,
  "metadata": {}
}
```

如果看到：

```json
{
  "executor": "LocalEchoExecutor",
  "model": "local-echo"
}
```

表示调用链路完成了，但真实模型没有成功使用，系统执行了 Echo 降级。

# 十四、取消和重试运行

## 1. 取消运行

在未结束的 Run 中点击“取消运行”。

对应：

```text
POST /api/runs/{run_id}/cancel
```

后端采用协作式取消：

```text
前端发起取消
    ↓
状态变为 cancel_requested
    ↓
图产生下一个事件
    ↓
后台任务检查最新状态
    ↓
停止执行并标记 canceled
```

这不是强制终止 Python 线程，因此可能不会在点击后瞬间停止。

## 2. 重试运行

点击“重试运行”。

对应：

```text
POST /api/runs/{run_id}/retry
```

后端会创建新的 Run，并保留：

```text
parent_run_id
retry_count
retry_from
```

原运行记录不会被覆盖。

# 十九、验证技能

打开候选技能，点击“执行验证”。

对应：

```text
POST /api/skills/{skill_id}/validate
```

后端会执行当前已经实现的验证流程，并保存验证报告。

验证通过后，状态进入可发布阶段。

技能治理顺序应保持为：

```text
candidate
    ↓
validate
    ↓
validated
    ↓
publish
    ↓
published
```

没有验证通过的候选不能发布。

# 二十、批准并发布技能

点击“批准并发布”。

前端会把“连接设置”里的操作者作为：

```json
{
  "approved_by": "admin"
}
```

发送到：

```text
POST /api/skills/{skill_id}/publish
```

后端会检查：

- 技能是否存在
- 是否已验证
- 是否有审批人
- 是否满足生命周期状态约束

发布后，该技能才能被在线运行过程自动检索。

当前审批人仍由请求体传入，并不是完整登录系统产生的用户身份。`X-Actor` 和管理员密钥提供了最小审计与保护，但还不等同于完整 RBAC。

```text

```

```text

  ↓
50%
  ↓
```

# 二十五、推荐的完整使用顺序

第一次使用时，建议严格按照以下顺序：

```text
1. npm run dev
2. 进入连接设置，配置操作者和管理员密钥
3. 进入系统管理，确认模型资源配置
4. 在工具目录登记可用工具
5. 创建多个 Agent
6. 填写 Agent 系统提示词、模型和资源配置
7. 创建 Agent 之间的执行连接
8. 设置入口 Agent
9. 保存为工作流
10. 在工作流详情确认版本
11. 进入运行中心
12. 选择工作流并输入真实任务
13. 启动后台运行
14. 打开运行详情观察事件
15. 检查 executor，确认是否真实调用模型
16. 检查最终 State 和技能轨迹
17. 对失败 Run 执行重试
18. 从有效 Run 生成候选技能
19. 在技能治理中执行验证
20. 审核 Markdown 和验证报告
21. 批准并进行小比例灰度
22. 观察后续 Run
23. 扩大灰度或回滚
24. 在系统管理查看审计记录
25. 导出系统快照备份
```

最终形成的完整闭环是：

```text
工具登记
    ↓
Agent 编排
    ↓
工作流保存与版本化
    ↓
用户提交任务
    ↓
真实模型图执行
    ↓
Context、Memory、Skill 注入
    ↓
事件和结果持久化
    ↓
运行轨迹复盘
    ↓
生成候选技能
    ↓
验证与人工审批
    ↓
灰度发布
    ↓
新任务复用技能
    ↓
继续产生新轨迹
```

这就是当前前端与后端已经能够落地执行的完整产品使用流程。
